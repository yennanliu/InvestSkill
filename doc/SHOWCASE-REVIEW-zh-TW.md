# InvestSkill 展示櫃 — 它是怎麼做出來的，以及該不該變成一個 Skill

> [English](SHOWCASE-REVIEW.md) · **繁體中文**
>
> **範圍：** 檢視姊妹專案 [`yennanliu/InvestSkill-test`](https://github.com/yennanliu/InvestSkill-test) 裡的繁體中文展示櫃（[線上版](https://yennj12.js.org/InvestSkill-test/showcase/index.html)）——它是什麼、如何產生、背後的思維、可重複使用的流程——並評估 InvestSkill 是否應該新增一個能產出這類內容的 skill。
> **日期：** 2026-11-15 · 檢視基準為 InvestSkill-test `0984b6e` 與 InvestSkill v1.14.1
> **性質：** 僅為檢視與建議。本文件不更動任何 skill、prompt 或網站檔案。

---

## 1. 摘要

- 展示櫃是**八個互相連結的報告頁面**，用同一份 2026-07-29 的**資料快照**，把框架目錄在一個四檔股票的籃子（MU、SKHY、MRVL、SNDL）上完整跑一遍。
- 它是**在一次 Claude 工作階段中寫成**的，之後才改寫成**決定性的 Python 產生器**（約 6,100 行，只用標準函式庫），CI 會把產生器的輸出與已提交的 HTML 逐位元組比對。建置時不會呼叫任何模型。
- 它的價值在思維，不在工具：單一共用快照、每個分數旁邊都附原始輸入、資料瑕疵原樣保留、工作流可以停下來說「沒有可做的設定」。
- **建議：現在不要新增「showcase」skill。** 展示櫃之所以可信，靠的是執行環境和一份已提交的真實個股資料，而 InvestSkill 刻意兩者都沒有。應該做的是從網站連結過去、把它的規則搬進既有的 prompt，等使用者真的要求多檔股票的交付物時，再考慮範圍較小的 `basket-report` 協調器（§7）。

## 2. 展示櫃是什麼

| 頁面 | 展示的框架 | 切入角度 |
|---|---|---|
| `index.html`（總覽） | 框架涵蓋地圖 | 四檔不相干的股票為何同一天下跌 7.8–9.6%；一個核心估值問題；每個框架用在哪裡 |
| `screener.html` | `stock-screener`、`sector-analysis`、`economics-analysis`、`result-validator` | 五個維度、22 個子因子，每個分數旁附原始輸入，每一項排除都具名說明 |
| `mu.html` | `full-report`（15 個模組）＋ `bear-case`、`position-ladder`、`catalyst-calendar`、`result-validator` | 旗艦報告：$820.53 的股價等於假設 80.4% 的營業利益率永遠維持、再給 15 倍本益比 |
| `skhy.html` | `result-validator` | 資料完整性稽核；報告拒絕給出目標價（47/100，LOW） |
| `mrvl.html` | 估值模組 | GAAP 與 non-GAAP 的落差；三種估值方法的結果相差一個數量級 |
| `sndl.html` | 價值篩選 | 價值陷阱：股價淨值比 0.30 倍，但淨值每年縮水 7.1% |
| `workflows.html` | Cookbook 工作流 A–G | 七條串接的工作流；C 與 D 在第一道閘門就停止 |
| `supply-chain.html` | `industry-map` | HBM 價值鏈：11 層、3 個瓶頸、4 個二階投資標的 |

籃子本身是刻意設計的：三檔記憶體／AI 半導體，各自說出不同的故事，再加上與 AI 毫無關係的 SNDL 當對照組。一個真實事件（2026-07-28 四檔同步跳空下跌）讓總覽頁有一個要回答的問題，而不只是一份報告索引。

## 3. 它是怎麼產生的

從 repo 歷史可以看到三個步驟，全部與 Claude 共同撰寫：

| 日期 | Commit | 發生了什麼 |
|---|---|---|
| 2026-07-29 | `10db869` | **撰寫。** 從單一 `yfinance` 快照寫出八個 HTML 頁面（+5,572 行）。當時產生器不在 repo 內。Commit 記錄了 30 項重點主張中有 29 項以程式對照原始資料檢核，並在過程中發現兩處需要修正（SNDL 的 `bookValue` 欄位比申報的資產負債表低 27%；MRVL 的 EV/EBITDA 重新計算為 58.3 倍）。 |
| 2026-07-29 | `593efa1` | **可重現性。** 產生器搬進 `scripts/showcase/`，快照以 fixture 的形式提交。新增 `site.yml` CI：已提交的 HTML 必須等於重新產生的結果、兩次產生必須逐位元組相同、每個頁面都要通過結構／連結／無障礙檢查。新增 125 個測試。 |
| 2026-08-05 | `58a33f1` | **設計調整。** 在已經完整的頁面上疊加動態效果（沒有 JavaScript 的讀者看到的就是最終狀態），並加入 SVG 流程圖與階段圖。工作流使用表改為由工作流定義推導，因而發現「15 個模組」的說法實際上只列了 14 個。 |

### 建置流程

```
fixtures/snapshot.json   每檔股票一次 yfinance 擷取（450 KB）：報價、4 個會計年度與 5 季的財報、
        │                持股、Form 4、選擇權鏈、分析師預估、^GSPC／^SOX
        ▼
derive.py                Piotroski、ROIC vs. WACC、三情境 DCF、22 個篩選子因子、最大痛點、
        │                綜合評分——每次建置都重新計算，從不存檔
        ▼
context.py               共用事實（跳空幅度、回檔幅度、循環常態化、內部人交易合計）、
        │                格式化函式、Data & Sources 表頭、可處理中日韓字寬的訊號框
        ▼
prose.py                 各檔股票的敘事文字：標語、投資論點、多方與空方論述
        │
        ▼
page_*.py + viz.py + shell.py    五個頁面樣板、手寫的 SVG 圖表、一套 CSS／JS 外殼
        │
        ▼
build.py [--check]       寫出 docs/showcase/*.html，或把重新產生的結果與它比對
```

這個結構帶來三個特性：

1. **建置時沒有模型。** LLM 的成果凍結在 `prose.py` 與頁面樣板裡。建置是快照的純函式，不需要 API 金鑰，也不需要網路。
2. **沒有衍生數值檔。** 指標每次建置都從快照重新計算，所以不會與它引用的資料脫節。
3. **頁面自給自足。** 沒有 CDN、沒有圖表函式庫、沒有外部 script——每張圖都是內嵌 SVG，背後附資料表。

## 4. 思維

以下是值得借用的想法，大致依價值排序。

1. **單一快照、單一資料日期。** 每個頁面都讀同一個檔案，所以不會有兩份報告對同一檔股票引用不同的價格。
2. **呈現推導過程，而不只是分數。** 22 個篩選子因子各自附上原始輸入；綜合評分列出「權重 × 子分數」的算式；DCF 附上敏感度表。
3. **缺漏的數值絕不以中性的 5.0 填補。** 無法評分的維度標示為「未評估」，並顯示重新正規化後的權重。
4. **保留瑕疵，讓驗證器去抓。** 以韓元申報的財報對上美元計價的 ADR、只有 13 天的價格歷史、與申報文件不符的資料商欄位，全部保留並標示。資料清乾淨的展示櫃會讓 `result-validator` 無事可做。
5. **拒絕也是一種有效結果。** 工作流 C（股息組合）與 D（波段做多）在第一道閘門就停止；SKHY 沒有目標價。頁面把這些呈現為框架正常運作。
6. **從一個問題出發。** 總覽頁問的是：$820 究竟是 5.3 倍的前瞻本益比，還是 16.6 倍的歷史平均盈餘？每個頁面都對著這個問題定位。
7. **產生的就是產生的。** 手動編輯 HTML 沒有意義，因為 CI 會把它還原；要改頁面只能改產生器。
8. **裝飾不承擔內容。** 動畫只會把內容換成相同的內容；列印、減少動態效果與無 JavaScript 的讀者看到的都是完成的頁面。

## 5. 流程，整理成步驟

給想在另一個籃子上重做一次的人：

1. **為了對比而挑選籃子**——一個主題、主題中不同的位置，再加一個刻意的異類。
2. **擷取一份快照**並提交。把資料日期固定成常數。
3. **先計算，後撰寫。** 在任何敘事出現之前，先把每個指標寫進程式。
4. **依相依順序執行框架**（商業品質 → 估值 → 市場訊號 → 技術面 → 風險）；Beta 與資本結構決定 WACC，WACC 決定 DCF，DCF 決定進場區間。
5. **依據算出來的數字撰寫敘事**，再以程式檢核重點主張。
6. **發布前先稽核**——每份綜合結論都跑 `result-validator`，信賴分數偏低時放在頁面最上方。
7. **用 CI 把關**——產生結果等於已提交內容、產生結果具決定性、連結與結構有效。

## 6. 目前展示櫃的限制

以下是閱讀產生器時發現的；從頁面上都看不出來。

- **敘事中的數字不是算出來的。** `prose.py` 以純文字寫了約 430 個金額數字，幾乎沒有任何插值。表格與圖表由快照推導，句子則不是，也沒有測試比對兩者。「每個數字都重新計算」只對資料層成立。30 項中 29 項的檢核只在撰寫當時跑過一次。
- **總覽頁誇大了自動化程度。** 它說四個產生步驟全部在 GitHub Actions 內完成、無人工介入。該 repo 的排程工作流產生的是 `output/` 底下的 Markdown 報告；展示櫃是在工作階段中寫成的，CI 只負責驗證。
- **它停在 v1.11.0。** 涵蓋 27 個框架。目前有 11 個 skill 沒有出現在任何頁面：`compare`、`credit-check`、`earnings-preview`、`etf-analysis`、`fact-check`、`forensic-accounting`、`learning-coach`、`risk-stress-test`、`tax-lens`、`thesis-tracker`、`trade-postmortem`。`full-report` 以 15 個模組呈現；現在 comprehensive 深度會跑 25 個。
- **資料來源是資料商。** `yfinance` 很方便，但展示櫃自己就發現它有一個欄位與申報文件差了 27%。InvestSkill 自己的指引是使用一手來源（EDGAR、公司投資人關係網站、FRED）。
- **只有繁體中文**，而且快照距今已三個半月。
- **InvestSkill 沒有連結到它。** 這個 repo 與它的網站上都找不到對展示櫃的任何引用。

## 7. InvestSkill 該不該新增這樣的 skill？

### 「這樣的 skill」可能是什麼

| 選項 | 內容 | 結論 |
|---|---|---|
| **A. 把 `showcase` 做成分析框架** | 一個 prompt，輸入一個籃子，寫出總覽、篩選、各檔報告、工作流與產業鏈地圖 | **不要** |
| **B. 移植產生器** | 把 `scripts/showcase/` 與快照搬進這個 repo | **不要** |
| **C. `basket-report` 協調器** | 輸出類 skill（類似 `report-generator`），把 `stock-screener` → `compare` → 各檔的 `full-report` → `industry-map` 串成一份互相連結的 HTML 交付物 | **還不要** |
| **D. 採用它的做法，並連結展示櫃** | 不新增 skill | **現在就做** |

### 為什麼不選 A 或 B

- **有價值的部分無法寫成 prompt。** 展示櫃的可信度來自逐位元組相同的重建與 CI 比對。Prompt 兩者都無法保證；要求模型「產生一個展示櫃」，得到的頁面看起來一樣，卻沒有任何一項保證。
- **它與兩條既有規則衝突。** InvestSkill 沒有執行環境、任何 skill 都不擷取資料，而且從不提交真實個股的資料（`data/fixtures/` 只放虛構的 ZEPH 資料包）。選項 B 兩條都違反，還會在一個零相依的 Node repo 裡加進 Python 工具鏈。
- **它不是一種分析。** 它本身不產生訊號，所以會是一個不計入 34 個框架的輸出工具，卻仍要付出新增 skill 的完整成本：兩種語言、三個平台設定檔、網站頁面、prompt 預算與合約檢查。
- **每次執行的成本非常高。** 四檔股票跑 comprehensive 深度，在總覽、篩選與工作流之前就已經是 100 次模組執行。這放不進單一 context window，所以 skill 必須指示模型儲存並重新載入中間檔案——而這正是 `full-report` 對單一股票已經在做的事。
- **大部分功能已經存在。** `full-report` 涵蓋單一股票的 HTML 報告，`compare` 與 `stock-screener` 涵蓋籃子排名，`industry-map` 涵蓋產業鏈，`report-generator` 涵蓋 HTML 輸出。

### 真正的缺口，以及選項 C

目前有一樣東西沒有歸屬：**多檔股票的交付物**。`compare` 與 `stock-screener` 的結果是 Markdown，`full-report` 只接受一檔股票。想要「這四檔、一份互相連結的報告」的使用者，只能自己動手拼。

如果這個需求真的出現，合適的形式是一個小型協調器，而不是展示櫃：

- 上限為 2–5 檔股票，每檔使用 `standard` 深度；
- 整個籃子共用一個 `Data & Sources` 表頭與資料日期；
- 一個總覽頁，說明要回答的問題、`compare` 的排名，並連結到各檔的報告；
- 歸類在 `scripts/lib/skill-registry.js` 的 `OUTPUT_TOOLS`，讓對外宣稱的框架數維持 34 個。

只有在確定有人需要之後才值得做，因為它會是這個 plugin 中執行與評估成本最高的 skill，而且現有的即時評估工具是為了在 ZEPH 資料包上跑單一股票的 skill 而設計的。

### 建議現在做的事（選項 D）

1. **從網站的示範區連結到展示櫃**，英文與繁體中文都要，並標明快照日期與框架版本。
2. **把規則搬進既有的 prompt**，補上缺少的部分。`full-report` 已經會對未評分的模組重新加權，而不是使用中性值；但它還沒有要求同一次執行中的所有模組必須共用單一資料日期的快照。請檢查 `stock-screener` 與 `compare` 是否有「每個分數旁附原始輸入」，以及 Cookbook 工作流是否有「閘門讓工作流停止也是一種結果」。
3. **在展示櫃自己的 repo 修正它**：讓敘事中的數字由快照推導（或以測試比對）、更正總覽頁對自動化的說法，並更新到目前的 34 個框架與 25 個模組的 `full-report`。
4. **讓展示櫃留在原處。** 一個有自己的執行環境與已提交資料的姊妹 repo，正是它該在的地方；正因為有這層分隔，InvestSkill 才能維持純 prompt 的 plugin。
